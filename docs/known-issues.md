## 1. 自動化の許可ダイアログが実機でどう見えるかは未確認

警告段階の `tell application "System Events" to log out` は macOS の「自動化」の許可を要求する。
許可の有無は `stage warn` が `automation ok` / `automation denied` として出すようにし、
与え方も README に書いた。残っているのは実機の挙動。

- 影響: 小に下がった（気づけない状態ではなくなった）
- 未確認: **root の LaunchDaemon から `launchctl asuser` 経由で叩いたとき、許可ダイアログが
  GUI ユーザーに出るのか**。誰にも見えないまま失敗し続ける可能性がある
- 未確認: 許可が無いとき `osascript` が本当に非ゼロで終わるか（エラー -1743 を想定して
  いるが、こちらでは拒否状態を再現していない。テストはスタブで模しているだけ）。
  **ここが違っていると検出そのものが効かない**
- 限界: 判定は `asuser`（`launchctl asuser` + `sudo -u`）越しの失敗をまとめて
  `automation denied` と読む。許可以外の理由で `asuser` が失敗しても同じ表示になる。
  想定している経路（root の LaunchDaemon、`sudo` 付きの `stage warn`）では区別が要らない
  ので分けていない
- 確認手順: [verify-on-device.md](verify-on-device.md) の 1

## 2. 「本番で本当に落ちるか」は 1 回試すしかない

`rehearsal` はすべてドライランなので、`shutdown -h now` が実行される経路だけは
本番で 1 回試すまで確認できない。

事後の可視化は入れた: 本番で enforce まで到達するとログに `enforce reached level=…` を
残し、`status` が「本番到達」として最後の日時を出す。メニューバーアプリも同じものを
「最後に本番で実行」として出す。スクリプトが `shutdown` を呼ぶところまでは
`reached: production normal invokes shutdown` がスタブで見ている。

**残る点は変わらない。** 「本番到達」は落ちた**あと**に埋まるので、導入した時点で
「効くかどうか」を先に知る手段にはならない。実際に電源が落ちるかは OS 側の話で、
こちらのテストでは届かない。

- 影響: 中 → 小（気づけない期間が「ずっと」から「初回まで」に縮んだ）
- 未確認: 実機で 1 回落とすまでは、`shutdown -h now` が通ることを確認していない
- 確認手順: [verify-on-device.md](verify-on-device.md) の 2

## 3. 猶予の内側で再起動したときの挙動が未確認

`launchd.plist(5)` に書いてあるのは**スリープ**の場合だけで、「取りこぼした分は復帰時に 1 回に
まとめて実行する」とある。**電源オフから起動したときに取りこぼし分が流れるかは man に記述が無く、
こちらでも未確認**。もし流れるなら、強制終了された直後（猶予の内側）に電源を入れると
また落ちる。既定の猶予は 10 分なので、最長 10 分のあいだ起動できない状態になりうる。

- 影響: 中。ただし復旧手段は確実にある
- 復旧: 猶予（既定10分）を過ぎてから起動すれば必ず通常どおり立ち上がる。
  時間帯の判定は実行時の時計で行うので、窓を出てしまえば何も起きない。
  急ぐなら起動直後に `sudo touch /etc/enddayd.dryrun`（強制終了前のアラートが 10 秒あるので、
  その間に打てる）
- 対応案: 起動から N 分は enforce しない、という条件を足せば塞げる。ただし
  「再起動すれば逃げられる」経路を同時に作ることになるので、実際に起きると分かってから入れる
- 確認手順: [verify-on-device.md](verify-on-device.md) の 3

## 4. 日をまたぐ猶予に対応していない（警告は出す）

`強制終了 23:55` + `猶予 10分` は `24:05` にならず、実質 `23:59` で切れる。

黙ってはいない: `enddayd.sh` の `config` / `status` と、走るたびのログ（`config warning`）、
メニューバーアプリの設定画面とメニューが「実際に受け付けるのは 4 分です」と出す。
**拒否はしない。** 拒否するとその日から強制終了ごと効かなくなり、実害のほうが大きい。

- 影響: 小。そんな時刻に設定する人がいるかは別問題
- 判断待ち: 猶予を日跨ぎに対応させるかどうか。**翌日の曜日判定をどう扱うかが決まらない**
  （金曜 23:55 の猶予が土曜に伸びたとき、土曜が対象外なら発火しないのが正しいのか、
  金曜の続きとして発火すべきなのか）。決まるまでは警告で足りると判断した

## 5. 導入経路に本物を通すテストが無い

解除側（`uninstall`、ドライラン旗による非常停止）はテストで見ているが、**入れる側**は
本物を通すテストが無い。`install_self` は `install -o root -g wheel` が root を要求するため、
サンドボックスでは通せない。

分岐だけは見るようにした: `install(1)` をスタブに差し替える `as_root_installable` を足し、
「導入済みかどうかでモードをどう扱うか」を `install: …` の 3 件で守っている。
`load_daemon` 側も `/bin/launchctl` に揃えたのでスタブへ差し替わるようになり、
絶対パスから外れる退行は `lint: launchctl is always invoked by absolute path` が止める。

ただし **スタブが通っただけ**で、本物の `install` が失敗する条件（権限、`/usr/local/bin` の
不在、SIP 配下への配置）は再現していない。

- 影響: 中 → 小（分岐の退行は捕まるようになった）
- 判断待ち: 本物を通すには root で走る CI か、コンテナ相当の隔離が要る。macOS ランナーで
  `sudo` を使う手はあるが、**本物と差し替えたスタブが通っただけになりやすい**という
  元の懸念は消えない。費用対効果を見てから決める
- 現状の担保: 実機での `setup` → `rehearsal` を人が 1 回通す

## 6. 設定エラーのアラートは GUI が無いと出ない（対応しない）

`console_alert` は GUI ログイン中のユーザーがいなければアラートを出せない。

- 判断: **仕様として妥当なので直さない。** そもそも GUI が無ければ終業もクソもない
- ただし諦めたことはログに残すようにした（`alert skipped (no gui user)`）。
  残さないと、ログに「設定が読めません」とあるのに画面には何も出ていない状況で、
  アラートを出したつもりなのか出せなかったのかが区別できない

## 7. Windows 実装が無い（対象外）

`docs/windows.md` は移植する人向けのメモで、実装ではない。

- 判断: **対象外。** README に macOS 専用と明記済み。移植は別リポジトリでやる話
