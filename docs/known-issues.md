# 未対応の課題

2026-08-15 のレビューで見つかったもののうち、**まだ直していない**もの。
リポジトリを公開したら 1 項目 = 1 issue として起こす前提で書いている。

各項目に「確認済み」と書いてあるのは実測した範囲。書いていないものはコードを読んだだけで、
再現手順までは踏んでいない。

---

## 1. ログが伸び続ける

`/var/log/enddayd.log` は追記のみでローテーションしない。1 日 4 行程度なので実害が出るのは
何年も先だが、`rehearsal` を繰り返すと増える。

- 影響: 小。`status` の `tail -n 10` は影響を受けない
- 対応案: `/etc/newsyslog.d/enddayd.conf` を install 時に置く。エラーログ側も同じ
- 判断: 単独では優先度が低い。他の変更のついでに入れる

## 2. `logout` の自動化許可について何も書いていない

警告段階の `tell application "System Events" to log out` は macOS の「自動化」の許可を要求する。
許可されていない場合、スクリプトはログに `logout request failed` と書いて先へ進む（設計どおり
止まらない）。ただし **root の LaunchDaemon から `launchctl asuser` 経由で叩いたときに許可
ダイアログがどう見えるかは未確認**。

- 影響: 中。ログアウト試行が常に失敗していても気づきにくい
- 対応案: `rehearsal` の warn 段階で、成否をもっとはっきり出す。README に許可の与え方を書く
- 未確認: 実機で一度も許可していない状態からの初回挙動

## 3. `soft` は拒否されたらその日は落ちない

`soft` は未保存の書類があるとアプリ側で止まる。止まった場合、その日はもう強制終了しない
（launchd のトリガは強制終了時刻に 1 回だけで、猶予内の再試行は無い）。

README の表に「未保存があれば止まる」とは書いてあるが、「止まったら終わり」であることは
書いていない。仕様としては妥当だが、`soft` を選ぶ人は「粘って落としてくれる」と読む可能性がある。

- 影響: 中（誤解を招く）
- 対応案: README に明記する。または猶予内に再試行する（設計判断が要る）

## 4. 日をまたぐ猶予を定義していない

`強制終了 23:55` + `猶予 10分` は `24:05` にならず、実質 `23:59` で切れる。設定の検証でも
弾いていない。

- 影響: 小。そんな時刻に設定する人がいるかは別問題
- 対応案: 検証で警告を出すか、猶予を日跨ぎに対応させる

## 5. 導入経路にテストが無い

解除側（`uninstall`、ドライラン旗による非常停止）はテストで見ているが、**入れる側**は
テストが無い。`install_self` は `install -o root -g wheel` が root を要求し、`load_daemon` は
本物の `launchctl bootstrap` を叩くため、サンドボックスでは通せない。

- 影響: 中。導入まわりの退行はテストでは捕まらない
- 対応案: `install`/`launchctl` をスタブ化すれば書けるが、本物と差し替えたスタブが
  通っただけになりやすい（実機の失敗は再現しない）。費用対効果を見てから判断する
- 現状の担保: 実機での `setup` → `rehearsal` を人が 1 回通す

## 6. 「本番で本当に落ちるか」は 1 回試すしかない

`rehearsal` はすべてドライランなので、`shutdown -h now` が実行される経路だけは
本番で 1 回試すまで確認できない。

- 影響: 中。導入直後に「効かない」ことに気づけない可能性がある
- 対応案: `status` に「本番モードで最後に enforce まで到達した日時」を出す。
  到達していれば、少なくとも経路は生きていると分かる

## 7. 設定エラーのアラートは GUI が無いと出ない

`console_alert` は GUI ログイン中のユーザーがいなければ黙って諦める。ログには残るが、
画面には何も出ない。

- 影響: 小（そもそも GUI が無ければ終業もクソもない）
- 対応案: 不要かもしれない。記録として残す

## 8. bats のバージョンを 1.13.0 に固定した

`bats 1.11` 以降はテスト名に非 ASCII が含まれるとそのテストを読み飛ばす。テスト名を ASCII に
したので現在は問題ないが、CI をバージョン固定にしたので追随の判断がいつか要る。

- 影響: 小
- 対応案: 定期的に上げる。`tests/run.sh` の件数突き合わせがあるので、読み飛ばしが起きれば落ちる

## 9. 記事の下書きが実装と揃っていない

`docs/zenn-article.md` の抜粋コードは元から簡略版（時刻を直書き、レベル分岐なし）だが、
今回の修正で差がさらに広がった。特に次の 2 点は記事の主張そのものに関わる。

- `enforce` の抜粋が `sleep 2` → `shutdown` のままで、**落とす前にアラートを出す**現在の挙動を
  反映していない
- 設定の検証について記事に記述が無い

- 影響: 公開前に直せば無害。公開後に直すと読者の手元と食い違う
- 対応: 記事を仕上げるときに一緒に見直す（今回は記事に手を入れていない）

## 10. 猶予の内側で再起動したときの挙動が未確認

`launchd.plist(5)` に書いてあるのは**スリープ**の場合だけで、「取りこぼした分は復帰時に 1 回に
まとめて実行する」とある。**電源オフから起動したときに取りこぼし分が流れるかは man に記述が無く、
こちらでも未確認**。もし流れるなら、強制終了された直後（猶予の内側）に電源を入れると
また落ちる。既定の猶予は 10 分なので、最長 10 分のあいだ起動できない状態になりうる。

- 影響: 中。ただし復旧手段は確実にある
- 確認方法: 本番で初めて落ちた直後に電源を入れてみる。もう一度落ちれば「流れる」
- 復旧: 猶予（既定10分）を過ぎてから起動すれば必ず通常どおり立ち上がる。
  時間帯の判定は実行時の時計で行うので、窓を出てしまえば何も起きない。
  急ぐなら起動直後に `sudo touch /etc/enddayd.dryrun`（強制終了前のアラートが 10 秒あるので、
  その間に打てる）
- 対応案: 起動から N 分は enforce しない、という条件を足せば塞げる。ただし
  「再起動すれば逃げられる」経路を同時に作ることになるので、実際に起きると分かってから入れる

`docs/windows.md` は移植する人向けのメモで、実装ではない。

- 影響: 対象外（README に明記済み）
