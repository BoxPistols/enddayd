# 未対応の課題

2026-08-15 のレビューで見つかったもののうち、**まだ直していない**もの。
リポジトリを公開したら 1 項目 = 1 issue として起こす前提で書いている。

各項目に「確認済み」と書いてあるのは実測した範囲。書いていないものはコードを読んだだけで、
再現手順までは踏んでいない。

## 1. ログが伸び続ける

`/var/log/enddayd.log` は追記のみでローテーションしない。1 日 4 行程度なので実害が出るのは
何年も先だが、`rehearsal` を繰り返すと増える。

- 影響: 小。`status` の `tail -n 10` は影響を受けない
- 対応案: `/etc/newsyslog.d/enddayd.conf` を install 時に置く。エラーログ側も同じ
- 判断: 単独では優先度が低い。他の変更のついでに入れる

## 2. 自動化の許可ダイアログが実機でどう見えるかは未確認

警告段階の `tell application "System Events" to log out` は macOS の「自動化」の許可を要求する。
許可の有無は `stage warn` が `automation ok` / `automation denied` として出すようにし、
与え方も README に書いた。残っているのは実機の挙動で、**root の LaunchDaemon から
`launchctl asuser` 経由で叩いたときに許可ダイアログがどう見えるかは未確認**。

- 影響: 小に下がった（気づけない状態ではなくなった）
- 未確認: 実機で一度も許可していない状態からの初回挙動。ダイアログが GUI ユーザーに
  出るのか、誰にも見えないまま失敗するのか
- 未確認: 許可が無いとき `osascript` が本当に非ゼロで終わるか（エラー -1743 を想定して
  いるが、こちらでは拒否状態を再現していない。テストはスタブで模しているだけ）
- 限界: 判定は `asuser`（`launchctl asuser` + `sudo -u`）越しの失敗をまとめて
  `automation denied` と読む。許可以外の理由で `asuser` が失敗しても同じ表示になる。
  想定している経路（root の LaunchDaemon、`sudo` 付きの `stage warn`）では区別が要らない
  ので分けていない

## 3. 日をまたぐ猶予に対応していない

`強制終了 23:55` + `猶予 10分` は `24:05` にならず、実質 `23:59` で切れる。

メニューバーアプリ側は黙らなくなった: `ConfParser.warnings` が「実際に受け付けるのは
4 分です」と出す（設定画面とメニューの両方）。**拒否はしない**。拒否するとその日から
強制終了ごと効かなくなり、実害のほうが大きいため。

- 影響: 小。そんな時刻に設定する人がいるかは別問題
- 残り: **デーモン単体（`enddayd.sh`）にはまだ警告が無い**。CLI だけで使っている場合は
  気づけない。`validate_conf` は成否しか返さないので、警告の経路を作る必要がある
- 対応案: 猶予を日跨ぎに対応させる案もあるが、翌日の曜日判定をどう扱うかが決まらない
  （金曜 23:55 の猶予が土曜に伸びたとき、土曜が対象外なら発火しないのが正しいのか）

## 4. 導入経路にテストが無い

解除側（`uninstall`、ドライラン旗による非常停止）はテストで見ているが、**入れる側**は
本物を通すテストが無い。`install_self` は `install -o root -g wheel` が root を要求するため、
サンドボックスでは通せない。

分岐だけは見るようにした: `install(1)` をスタブに差し替える `as_root_installable` を足し、
「導入済みかどうかでモードをどう扱うか」を `install: …` の3件で守っている。ただし
**スタブが通っただけ**なので、本物の `install` が失敗する条件（権限、`/usr/local/bin` の
不在、SIP 配下への配置）は再現していない。

`load_daemon` 側は塞いだ: 呼び出しを `/bin/launchctl` に揃えたので
`tests/helper.bash` の置換がスタブへ差し替わるようになった（以前は素の `launchctl` が
残っていて本物を叩いていた）。絶対パスから外れる退行は
`lint: launchctl is always invoked by absolute path` が全出現の走査で止める。
ただし **`load_daemon` 自体のテストはまだ無い**（書ける状態になっただけ）。

- 影響: 中。導入まわりの退行はテストでは捕まらない
- 対応案: `install` をスタブ化すれば書けるが、本物と差し替えたスタブが
  通っただけになりやすい（実機の失敗は再現しない）。費用対効果を見てから判断する
- 現状の担保: 実機での `setup` → `rehearsal` を人が 1 回通す

## 5. 「本番で本当に落ちるか」は 1 回試すしかない

`rehearsal` はすべてドライランなので、`shutdown -h now` が実行される経路だけは
本番で 1 回試すまで確認できない。

事後の可視化は入れた: 本番で enforce まで到達するとログに `enforce reached level=…` を
残し、`status` が「本番到達」として最後の日時を出す。ここに日時があれば、少なくとも
到達する経路は生きていると分かる。スクリプトが `shutdown` を呼ぶところまでは
`reached: production normal invokes shutdown` がスタブで見ている。

**残る点は変わらない。** 「本番到達」は落ちた**あと**に埋まるので、導入した時点で
「効くかどうか」を先に知る手段にはならない。実際に電源が落ちるかは OS 側の話で、
こちらのテストでは届かない。

- 影響: 中 → 小（気づけない期間が「ずっと」から「初回まで」に縮んだ）
- 未確認: 実機で 1 回落とすまでは、`shutdown -h now` が通ることを確認していない

## 6. 設定エラーのアラートは GUI が無いと出ない

`console_alert` は GUI ログイン中のユーザーがいなければ黙って諦める。ログには残るが、
画面には何も出ない。

- 影響: 小（そもそも GUI が無ければ終業もクソもない）
- 対応案: 不要かもしれない。記録として残す

## 7. bats のバージョン固定の追随

`bats 1.11` 以降はテスト名に非 ASCII が含まれるとそのテストを読み飛ばす。テスト名を ASCII に
したので現在は問題ない。CI は npm の `bats@1.13.0` で固定している。

2026-08-16 時点で **1.13.0 は npm の最新**なので、いま上げる先は無い（`npm view bats version`）。
ただし Homebrew の `bats-core` は先を行っており、手元だけ新しくなることがある。
1.14.0 でも全件通ることは確認済み。

- 影響: 小
- 対応: 上げるときは `npm view bats version` で実在を確認してから書き換える。
  `bats-core` は npm に無いので、Homebrew の版数をそのまま書くと CI が壊れる
- 現状の担保: `tests/run.sh` の件数突き合わせがあるので、読み飛ばしが起きれば落ちる

## 8. 記事の下書きが実装と揃っていない

`docs/zenn-article.md` の抜粋コードは元から簡略版（時刻を直書き、レベル分岐なし）だが、
今回の修正で差がさらに広がった。特に次の 2 点は記事の主張そのものに関わる。

- `enforce` の抜粋が `sleep 2` → `shutdown` のままで、**落とす前にアラートを出す**現在の挙動を

- 影響: 公開前に直せば無害。公開後に直すと読者の手元と食い違う
- 対応: 記事を仕上げるときに一緒に見直す（今回は記事に手を入れていない）

## 9. 猶予の内側で再起動したときの挙動が未確認

`launchd.plist(5)` に書いてあるのは**スリープ**の場合だけで、「取りこぼした分は復帰時に 1 回に
まとめて実行する」とある。**電源オフから起動したときに取りこぼし分が流れるかは man に記述が無く、
こちらでも未確認**。もし流れるなら、強制終了された直後（猶予の内側）に電源を入れると
また落ちる。既定の猶予は 10 分なので、最長 10 分のあいだ起動できない状態になりうる。

- 影響: 中。ただし復旧手段は確実にある
- 確認方法: 本番で初めて落ちた直後に電源を入れてみる。もう一度落ちれば「流れる」
- 復旧: 猶予（既定10分）を過ぎてから起動すれば必ず通常どおり立ち上がる。
  時間帯の判定は実行時の時計で行うので、窓を出てしまえば何も起きない。
  急ぐなら起動直後に `sudo touch /etc/enddayd.dryrun`（強制終了前のアラートが 10 秒あるので、
  その間に打てる）
- 対応案: 起動から N 分は enforce しない、という条件を足せば塞げる。ただし
  「再起動すれば逃げられる」経路を同時に作ることになるので、実際に起きると分かってから入れる
